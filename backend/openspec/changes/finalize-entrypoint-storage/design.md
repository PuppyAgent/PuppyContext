## Scope and approval
This implements the already accepted 049 D01–D06 / 058 final mapping under the user's explicit full-completion instruction. 049 was unassigned and its prior worktree was clean. The sole implementation remains under that issue; 053/061 deliverables are reused, and 062 work is not overwritten. Remote Qubits operations have been requested separately; main/production is not authorized.

## Release A — Expand and reviewed data
Add import_database_sources and owner-only transitional cutover/decision tables. An inventory exports only IDs, domain-relevant facts and PostgreSQL SHA-256 fingerprints; config and credential values are not printed. Every old binding row requires an explicit reviewed disposition (synchronize/import/both), evidence reference and matching row+run snapshot. No default classification from provider, trigger, path or equal IDs is permitted.

Import copies preserve the complete encrypted config envelope, timestamps, creator/tenant and source ID. A dual-use decision explicitly supplies its Import source ID and stores synchronize_binding_id as a real FK; equal IDs alone imply nothing. Import-only rows must have no run, last-run, cursor, OAuth, external-source, Scope or scheduled/realtime facts that would be lost. Ambiguous cases stop before any data/receipt mutation. Dual-use bindings remove only the reserved Import config fields after copying them; history is never rewritten. An unsupported historical binding requires an explicit read-only retention reason and remains non-executable.

The operator stops producers and drains work, records a restore point and reviewed consumer manifest, then freezes affected writes. A guarded trigger blocks application writes through the old schema; the migration runner uses an owner-only transaction token. A database flag is not proof that processes stopped: actual process/queue evidence is still required. Locks and snapshot checks reject writes/runs changed after review. The real portable runner atomically verifies the copy and writes its immutable receipt. It does not delete the old rows yet.

## Release B — Contract and application
Promote the existing 20260927 contract byte-for-byte, then the new final Contract only after receipts/current postconditions and consumer exit are verified. Rename tables/columns in place, preserving FKs/IDs/ACLs; update explicit function bodies, indexes, trigger/policy names and the security-invoker Activity view. Remove Import-only rows only after exact-copy verification under locks. Remove decision/freeze tables/functions after their evidence is retained outside the live schema. Switch all repositories and direct consumers to final names without fallback. Remove old HTTP/DTO adapters and assert they no longer serve the old protocol.

Fresh installation applies the same final schema with no old-data receipt only when there is no legacy/user footprint. Populated upgrades must use separate Expand/data and Contract releases; a direct all-at-once push fails closed. Release pointers must select the final artifact instead of re-running an obsolete verifier against renamed tables.

## Recovery and acceptance
Before Contract, stop new writes before resuming old consumers; the old binding rows are still intact. After Contract, do not run an old application against renamed schema: restore the reviewed database/object-store point with matching old binaries, or roll forward with a final-schema-compatible build. Test restoration and post-cutover data preservation on owned disposable infrastructure. Keep installation, source tests, local deployment and hosted rollout as distinct evidence classes. No migration logs contain credentials or user config.
